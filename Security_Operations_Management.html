Theory

7 Types of Cyber Security Threats

1. Malware

Malware (Malicious Software) is any software designed to harm, exploit, or compromise systems. It's the umbrella term — everything below is a subset.

TypeBehaviorSelf-Replicates?Needs User?Example
VirusAttaches to legitimate files, executes when host file runsYesYes (must open file)ILOVEYOU, Melissa
WormSpreads across networks independentlyYesNo (self-propagates)WannaCry, Conficker, Stuxnet
TrojanDisguised as legitimate software, creates backdoorNoYes (install/run)njRAT, DarkComet
RansomwareEncrypts files, demands payment for decryptionSometimesUsually yesWannaCry, LockBit, REvil
SpywareSilently collects user data (keystrokes, screens)NoUsually noPegasus, FinFisher
RootkitHides deep in OS kernel, conceals other malwareNoNoNecurs, ZeroAccess
FilelessLives in memory only, uses legitimate tools (PowerShell, WMI)NoUsually noPowerShell Empire attacks
RATRemote Access Trojan — full remote control of victimNoYes (install)njRAT, AsyncRAT, Quasar

2. Emotet

Emotet deserves its own category because it's one of the most dangerous and sophisticated malware families. Originally a banking trojan (2014), it evolved into a malware-as-a-service platform. How it works: Spreads via phishing emails with malicious Word documents (macros). Once installed, it downloads additional payloads (TrickBot, Ryuk ransomware). Acts as a botnet — thousands of infected machines controlled by attackers. Self-propagates across the network using stolen credentials and exploits. Why it matters: Emotet was so dangerous that a global law enforcement operation took it down in 2021 — but it came back. It's the poster child for "infection leads to ransomware."

3. Denial of Service (DoS/DDoS)

Overwhelm a system/server/network so legitimate users can't access it. Not about stealing data — it's about disruption.

LayerAttack TypeHow
L3/L4 VolumetricUDP Flood, ICMP Flood, DNS/NTP AmplificationSaturate bandwidth with massive traffic
L4 ProtocolSYN Flood, Ping of Death, Smurf AttackExhaust server's connection state table
L7 ApplicationHTTP Flood, Slowloris, RUDYExhaust application resources (web server threads, DB connections)

DoS: Single source. DDoS: Distributed — thousands of sources (botnet). Much harder to stop because you can't block one IP.

4. Man in the Middle (MITM)

Attacker positions themselves between two communicating parties, intercepting and potentially modifying traffic. Neither party knows the attacker is there.

Alice ←──── Attacker ────→ Bob (thinks they're (thinks they're talking to Bob) talking to Alice)

Methods: ARP Poisoning (redirect LAN traffic), DNS Spoofing (redirect to fake site), SSL Stripping (downgrade HTTPS to HTTP), Rogue Wi-Fi (Evil Twin AP), HTTPS Interception (fake certificate). Prevention: HTTPS everywhere, Certificate pinning, VPN, HSTS (HTTP Strict Transport Security), DNSSEC.

5. Phishing

Social engineering via fake emails/messages/websites to steal credentials, install malware, or trick users into actions.

TypeTargetChannel
PhishingMass — anyoneEmail
Spear PhishingSpecific individual/orgEmail (researched, personalized)
WhalingExecutives (CEO, CFO)Email
VishingAnyoneVoice/Phone
SmishingAnyoneSMS
BECFinance/accountingCompromised or spoofed executive email

6. SQL Injection

Injecting malicious SQL code into input fields that interact with a database. Exploits lack of input validation. Can read, modify, delete data, bypass authentication, or even execute OS commands.

# Normal query: SELECT * FROM users WHERE user='admin' AND pass='secret';
# Injected:     SELECT * FROM users WHERE user='admin' OR '1'='1' -- ' AND pass='anything';
# Result:       Returns all users — bypasses login!

Types: In-Band (Union-based, Error-based), Blind (Boolean, Time-based), Out-of-Band. Prevention: Parameterized queries/Prepared statements (NEVER concatenate user input into SQL), Input validation, WAF, Least-privilege DB accounts.

Indicators of Compromise (IoC)

IoCs are forensic evidence that a security breach has occurred. They are reactive — they tell you an attack has already happened or is in progress. Think of IoCs as the "crime scene evidence."

Examples of IoC

CategoryIoC Examples
NetworkUnusual outbound traffic, Communication to known C2 (Command & Control) IPs, DNS requests to suspicious domains, Unexpected data transfers at odd hours, Spikes in failed connections
Host/EndpointUnknown processes running, Registry changes, New scheduled tasks, Unexpected services installed, Files with known malware hashes, Unexpected high CPU/memory usage
FileMalicious file hashes (MD5, SHA-256), Known malware signatures, Suspicious file names in temp directories, Modified system files
EmailSender IP from known threat lists, Malicious attachment hashes, Phishing URLs, SPF/DKIM failures
AccountLogins from unusual locations, Multiple failed logins followed by success, Privilege escalation, Logins at unusual times, New admin accounts created

Indicators of Attack (IoA)

IoAs focus on detecting attacker behavior in real-time, regardless of the tools or malware used. They are proactive — they identify attacks as they're happening, based on intent and actions, not artifacts.

IoC vs IoA

AspectIoC (Indicator of Compromise)IoA (Indicator of Attack)
FocusEvidence AFTER an attackBehavior DURING an attack
NatureReactive (what happened)Proactive (what's happening now)
What it detectsSpecific artifacts: hashes, IPs, domainsAttack patterns: lateral movement, privilege escalation, reconnaissance
EffectivenessOnly known threats (signature-based)Known AND unknown threats (behavior-based)
Example"This file has hash XYZ which is known malware""A process is spawning cmd.exe from Excel — that's suspicious behavior regardless of the file hash"
LimitationAttackers change hashes/IPs constantly (polymorphism)May generate false positives
Mapped toThreat intelligence feeds, VirusTotalMITRE ATT&CK framework
💡 Interview Gold: "IoCs tell you the WHAT (what artifact was found). IoAs tell you the WHY and HOW (what behavior pattern is happening). A mature SOC uses BOTH — IoCs for known threats and IoAs for behavioral detection of novel attacks."

IoC Use in Detection & Response

  1. Threat Intel Feeds: Subscribe to feeds (MISP, OTX, STIX/TAXII) that share IoCs (malicious IPs, domains, hashes)
  2. SIEM Integration: Import IoCs into SIEM → create correlation rules → alert when IoC is seen in your logs
  3. EDR Matching: EDR tools compare file hashes and behaviors against IoC databases in real-time
  4. Incident Response: During IR, search your environment for IoCs related to the specific threat (e.g., after hearing about a new ransomware, search for its known hashes, C2 domains, registry keys)
  5. Threat Hunting: Proactively search logs for IoCs/IoAs without waiting for an alert

Important Operational Documents

  • Playbooks: Step-by-step procedures for handling specific incident types (phishing, malware, DDoS, unauthorized access). "If you see X, do Y."
  • Runbooks: Technical procedures for specific tasks (how to block an IP on the firewall, how to isolate a host, how to collect forensic image).
  • Standard Operating Procedures (SOPs): How the SOC operates day-to-day (shift handoff, escalation criteria, reporting timelines).
  • Communication Matrix: Who to notify for each severity level (P1=CISO, P2=SOC Manager, P3=Team Lead).
  • Escalation Policy: When to escalate, to whom, and within what timeframe.

Signature-Based vs Anomaly-Based Detection

Signatures: Match known patterns (like antivirus signatures). Fast, low false positives, but ONLY detects known threats. Anomaly: Establish a baseline of "normal" behavior, alert on deviations. Detects unknown/novel threats, but higher false positive rate. A mature SOC uses both.

Alert Triage Workflow

  1. Alert fires in SIEM based on correlation rule
  2. L1 reviews: Is this a true positive or false positive? Check context — source IP, destination, time, user, past history
  3. Enrich: Look up IPs (VirusTotal, AbuseIPDB), Check domain reputation, Correlate with other alerts
  4. Decision: False Positive → close with notes. True Positive → Create incident, escalate to L2
  5. Document: All actions, evidence, reasoning in the ticket

Incident Management Systems

TheHive (Open-Source Incident Management)

TheHive is a popular open-source Security Incident Response Platform. Works with Cortex (automated analysis) and MISP (threat intelligence).

# Key TheHive concepts:
# Case:       An incident being investigated. Contains tasks, observables, logs.
# Alert:      Incoming notification (from SIEM, email, etc.) that may become a case.
# Observable: An artifact to analyze — IP, domain, hash, email, URL.
# Task:       Work items within a case (analyze malware, contain host, write report).
# Playbook:   Pre-defined set of tasks for a specific incident type.
# TLP:        Traffic Light Protocol — sharing classification
#             TLP:RED (no sharing), TLP:AMBER (limited), TLP:GREEN (community), TLP:WHITE (public)

# Workflow:
# 1. Alert arrives (from SIEM, MISP, email)
# 2. Analyst reviews → Promotes to Case or Closes as False Positive
# 3. Case created with severity, TLP, tasks assigned
# 4. Observables added (IPs, domains, hashes)
# 5. Cortex analyzers run on observables (VirusTotal, MISP lookup, GeoIP)
# 6. Tasks completed, evidence documented
# 7. Case closed with resolution and report

Case and Alert Naming Convention

Use a consistent format: [DATE]-[CATEGORY]-[SHORT_DESCRIPTION]-[SEQ]
Example: 2026-07-01-MALWARE-Emotet-Phishing-Campaign-001
Or: INC-2026-0142-PHISHING

Zero Trust Architecture

"Never trust, always verify." Traditional security: Trust everything inside the network perimeter. Zero Trust: Trust nothing — verify every user, device, and connection regardless of location. Key principles: Verify explicitly (MFA, device health), Least privilege access, Assume breach (segment, monitor, detect). Implementation: Microsegmentation, Identity-based access, Continuous verification, Encrypted all traffic (even internal).

Understanding DNS (Port 53)

DNS Server Types

TypeRole
Stub ResolverBuilt into your OS. Sends queries to configured DNS server. Caches locally. Not a full resolver.
Forwarding ServerReceives queries from clients, forwards to another DNS server. Caches results. Doesn't resolve itself.
Caching ServerPerforms full recursive resolution, caches results. Speeds up repeated queries. Example: Unbound.
Authoritative ServerHolds the actual DNS records for a zone. Answers definitively: "I know the answer." Doesn't recurse.
Recursive ResolverResolves queries on behalf of clients by querying root → TLD → authoritative. Example: 8.8.8.8, 1.1.1.1.

HTTP and HTTPS Analysis

Decoding URLs

# URL structure:
https://user:pass@www.example.com:443/path/page.html?key=value&id=2#section
│       │         │                │   │              │            │
scheme  auth      host           port  path          query        fragment

# URL encoding: space=%20, <=<=%3C, >=%3E, '=%27, "=%22
# Attackers use encoding to bypass filters:
# %2F = /    %3A = :    %3F = ?    %26 = &
# Double-encoding: %252F = %2F → /

HTTP Request Analysis

# Key Request Headers to analyze:
GET /login HTTP/1.1
Host: target.com                  # Target website
User-Agent: Mozilla/5.0 (...)     # Client software — look for unusual/scripted agents
Referer: https://google.com/      # Where user came from — check for suspicious referrers
Cookie: session=abc123            # Session tokens — look for stolen/replayed sessions
X-Forwarded-For: 10.0.0.1        # Real client IP behind proxy
Content-Type: application/json    # Data format — watch for unexpected types

HTTP Response Analysis

# Key Response Headers:
HTTP/1.1 200 OK
Server: Apache/2.4.41            # Server version (info disclosure if detailed)
Set-Cookie: session=xyz; HttpOnly; Secure; SameSite=Strict
X-Frame-Options: DENY            # Clickjacking protection
Content-Security-Policy: default-src 'self'   # XSS protection
Strict-Transport-Security: max-age=31536000   # HSTS — force HTTPS

# Security headers to CHECK for presence:
# X-Frame-Options, CSP, HSTS, X-Content-Type-Options, X-XSS-Protection
# Missing headers = misconfiguration = risk

Analyzing HTTP for Suspicious Activity

  • Credential Phishing: POST to fake login page → check domain legitimacy, SSL certificate issuer
  • User-Agent Deconstruction: Automated tools often have unusual User-Agents (Python-urllib, curl/7.x, sqlmap). Mismatch: Windows User-Agent from a Mac = suspicious.
  • Exploit Kits: Chain of redirects (site → iframe → exploit → payload). Look for: Multiple 302 redirects, Obfuscated JavaScript, Unexpected iframes.
  • HTTPS Certificate Inspection: Self-signed cert, Cert doesn't match domain, Recently issued cert, Free CA (Let's Encrypt used by attackers — not inherently suspicious but combined with other factors).

SMTP & Email Analysis

How Email Works

Sender → [MUA] → [MSA/MTA] → [MTA] → ... → [MTA] → [MDA] → [MUA] → Recipient (Outlook) (smtp.gmail) (relay) (mx.target) (mailbox) (Outlook) Port 25: SMTP (server-to-server) Port 587: SMTP Submission (client-to-server, authenticated) Port 465: SMTPS (SMTP over TLS) Port 993: IMAPS (read email) Port 995: POP3S (download email)

Reading Email Headers (Bottom-Up)

# Headers are added bottom-to-top — read from BOTTOM to TOP to trace the path

Received: from mail-out.attacker.com (203.0.113.50)       ← FIRST hop (sender's server)
    by mx1.target.com (10.0.0.5)                          ← LAST hop (recipient's server)
    Thu, 01 Jul 2026 10:30:00 +0530

From: ceo@company.com           ← Can be spoofed!
Reply-To: attacker@evil.com     ← Where replies actually go — RED FLAG if different from From
Return-Path: bounce@evil.com    ← Bounce address — another spoofing indicator
X-Originating-IP: 203.0.113.50 ← Actual sender IP
Message-ID: <unique@server>    ← Should match sending domain
SPF: pass/fail                  ← Did sender IP match domain's SPF record?
DKIM: pass/fail                 ← Was email cryptographically signed by domain?
DMARC: pass/fail                ← Did email pass both SPF AND DKIM alignment?

Email Authentication (SPF, DKIM, DMARC)

ProtocolWhat It DoesHow
SPFSpecifies which IPs can send email for a domainDNS TXT record listing authorized senders. Receiver checks if sender IP is in the list.
DKIMCryptographic signature proving email wasn't tampered withSender adds signature using private key. Receiver verifies with public key from DNS.
DMARCPolicy that tells receivers what to do if SPF/DKIM failDNS TXT record: none (monitor), quarantine (spam), reject (drop). Requires alignment.

Identifying Spoofed Email

  1. Check From vs Return-Path vs Reply-To — do they match?
  2. Check SPF result — pass or fail?
  3. Check DKIM result — pass or fail?
  4. Check DMARC result — pass or fail?
  5. Check Received headers — does the originating IP match the claimed sender domain?
  6. Check X-Originating-IP — geolocate it, check reputation

Kerberos Authentication (for SOC)

1. User sends credentials to KDC (Key Distribution Center) 2. KDC's AS (Authentication Service) verifies → issues TGT (Ticket-Granting Ticket) 3. User presents TGT to TGS (Ticket-Granting Service) + requests access to service 4. TGS issues Service Ticket 5. Log Collection Pipeline

Source → Agent → Transport → Parser → Enrichment → Normalization → Storage → SIEM Source: Firewalls, Servers, Endpoints, Cloud, Apps Agent: Winlogbeat, Filebeat, NXLog, Fluentd, rsyslog Transport: Syslog (UDP 514), TCP, Kafka, HTTP Parser: Extract fields from unstructured logs (regex, Grok patterns) Enrichment: Add context: GeoIP, Threat Intel lookup, User info, Asset info Normalization: Map to common schema (ECS, CIM) so different sources speak same language Storage: Elasticsearch, Splunk indexes, Data lake SIEM: Correlation, Alerting, Dashboards

SIEM (Security Information & Event Management)

TheoryLab

What is SIEM?

A SIEM collects logs from across your entire environment, normalizes them into a common format, correlates events to find patterns, and generates alerts when suspicious activity is detected. It's the SOC's primary tool — the "brain" that connects the dots across all security data.

Benefits of Data Centralization

  • Single pane of glass: See all security data in one place instead of checking 20 different consoles
  • Correlation: Connect events across sources (failed login on AD + VPN login from unusual country + file download = compromised account)
  • Long-term storage: Retain logs for compliance and forensic investigations
  • Compliance: Prove to auditors that you're monitoring and retaining logs (PCI DSS, ISO 27001, CERT-In 180-day requirement)

Efficient Searching in SIEM

# ═══ Splunk SPL (Search Processing Language) ═══
index=security sourcetype=WinEventLog EventCode=4625
| stats count by src_ip, user
| where count > 10
| sort -count
# Translation: Find failed logins, count per IP+user, show those with >10 attempts

index=firewall action=blocked
| timechart span=1h count by src_ip
# Translation: Show blocked connections per hour per source IP

index=security EventCode=4720
| table _time, TargetUserName, SubjectUserName, ComputerName
# Translation: Show newly created accounts with who created them

# ═══ Elastic/KQL (Kibana Query Language) ═══
event.code: "4625" and source.ip: "203.0.113.*"
# Failed logins from specific subnet

event.code: "1" and process.name: "powershell.exe" and process.command_line: *-enc*
# Sysmon Process Creation: PowerShell with encoded commands (suspicious!)

# ═══ Microsoft Sentinel KQL ═══
SecurityEvent
| where EventID == 4625
| summarize FailedAttempts = count() by TargetAccount, IpAddress
| where FailedAttempts > 10
| order by FailedAttempts desc

TheoryLab

What is Cyber Threat Intelligence?

Threat Intelligence is evidence-based knowledge about existing or emerging threats that helps make informed security decisions. It's not raw data — it's data that has been collected, processed, analyzed, and contextualized to be actionable.

Data vs Information vs Intelligence

LevelWhatExample
DataRaw, unprocessed factsIP address 203.0.113.50 appeared in firewall logs
InformationData with contextIP 203.0.113.50 made 500 requests to /admin in 1 hour from Russia
IntelligenceAnalyzed, actionable insightIP 203.0.113.50 is part of APT28 infrastructure, targeting financial organizations. Block this IP range and hunt for similar patterns in your network.

Sharing Standards

  • STIX (Structured Threat Information eXpression): JSON format for describing threat intelligence (indicators, threat actors, campaigns, attack patterns, malware). The "language" of threat intel.
  • TAXII (Trusted Automated eXchange of Indicator Information): Transport protocol for sharing STIX data. Uses REST API. Defines Collection (data repo) and Channel (pub/sub). The "transport" of threat intel.
  • MISP (Malware Information Sharing Platform): Open-source platform for sharing, storing, and correlating threat intelligence. Supports STIX/TAXII.

MITRE ATT&CK Framework

A knowledge base of adversary Tactics, Techniques, and Procedures (TTPs) based on real-world observations. Organized as a matrix. Used to: Map detections to adversary behavior, Identify detection gaps, Structure threat hunting, Communicate about threats.

Lab — MISP Threat Intelligence Platform

# MISP — Malware Information Sharing Platform
# Web-based interface for creating, storing, and sharing threat intelligence

# Key MISP Concepts:
# Event:      A threat intelligence report (e.g., "Emotet Campaign July 2026")
# Attribute:  A single IoC within an event (IP, domain, hash, email, URL)
# Object:     Structured group of attributes (e.g., File object: name + hash + size)
# Tag:        Label for classification (TLP:GREEN, malware:emotet, source:cert-in)
# Galaxy:     Categorized knowledge (MITRE ATT&CK, Threat actors, Malware types)
# Correlation: MISP automatically links events that share common attributes

# Workflow:
# 1. Create Event (title, date, distribution, threat level, TLP)
# 2. Add Attributes (type: ip-dst, domain, md5, sha256, url, email-src)
# 3. Tag event (TLP, MITRE ATT&CK technique, malware family)
# 4. Correlate — MISP shows related events sharing same IoCs
# 5. Share — Publish to connected MISP instances or export as STIX/CSV
# 6. Integrate — Feed IoCs into SIEM (Splunk, Elastic, QRadar) for detection

# MISP API example (Python):
from pymisp import PyMISP
misp = PyMISP('https://misp.local', 'API_KEY', ssl=False)
event = misp.new_event(info="Emotet Campaign July 2026", distribution=1, threat_level_id=2)
misp.add_attribute(event, type='ip-dst', value='203.0.113.50')
misp.add_attribute(event, type='domain', value='evil-c2.com')
misp.add_attribute(event, type='md5', value='d41d8cd98f00b204e9800998ecf8427e')
