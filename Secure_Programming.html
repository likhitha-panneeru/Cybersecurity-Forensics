Session 1 — Browser Components, DOM/JS, HTTP, Cookies, HTTPS, QUIC, HTTP/2 & HTTP/3

Introduction to Components of a Browser

A browser is a client application that retrieves web resources, interprets them and presents an interactive page. For secure programming, understand the boundary between the browser/client, the network protocol and the server.

DOM

The Document Object Model (DOM) is the browser's structured representation of an HTML document. Elements become nodes in a tree that JavaScript can read and modify.

<button id="save">Save</button>
<script>
const button = document.getElementById("save");
button.textContent = "Saved";
</script>

Security relevance: DOM manipulation is central to understanding client-side injection issues, including DOM-based XSS.

JavaScript

JavaScript executes in the browser and can manipulate the DOM, respond to events and communicate with servers. Secure programming requires treating data received from users, URLs, storage and servers as potentially untrusted.

HTTP — the protocol

HTTP is an application-layer request/response protocol. A client sends a request; a server returns a response.

Request conceptExample
MethodGET, POST, PUT, DELETE
Path/URL/login
HeadersHost, Content-Type, Cookie
BodyCommonly used for submitted data
Status code200, 404, 500, etc.

HTTP History

HTTP history in browser/developer tooling helps examine previously made requests and responses. From a secure-development perspective, use it to understand what information the browser sends, what the server returns and where sensitive data appears.

HTTP/1.1

HTTP/1.1 standardized persistent connections and common mechanisms such as request methods, headers, status codes, caching and chunked transfer. It is important to recognize its text-oriented request/response structure.

Cookies for Stateful Requests

HTTP itself is stateless: individual requests do not inherently remember earlier requests. Cookies allow a server to associate subsequent requests with state, commonly through a session identifier.

Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax
Cookie: session_id=abc123

Important cookie attributes:

  • Secure: send the cookie over HTTPS connections.
  • HttpOnly: prevents ordinary JavaScript access to the cookie.
  • SameSite: controls cross-site cookie sending behavior.
  • Path/Domain: constrain where the cookie is sent.

HTTPS

HTTPS is HTTP carried over TLS. TLS provides confidentiality, integrity and server authentication when correctly configured. HTTPS protects traffic in transit; it does not automatically make the application itself secure.

QUIC

QUIC is a transport protocol built over UDP and designed for secure, multiplexed communications. It forms the transport foundation for HTTP/3.

HTTP/2

HTTP/2 uses a binary framing layer and supports multiplexing multiple streams over a connection, reducing some limitations of HTTP/1.1 connection handling.

HTTP/3

HTTP/3 maps HTTP semantics onto QUIC rather than TCP. Know the high-level relationship:

HTTP/1.1 → TCP-based traditional HTTP; HTTP/2 → TCP + binary multiplexed framing; HTTP/3 → QUIC over UDP.

Lab — Analyzing Web Components

  1. Open browser developer tools on a permitted test page.

  3. Inspect JavaScript loaded by the page.

  5. Identify method, URL, status code, headers and response body.

  7. Compare a normal HTTP request with an HTTPS request at the application level.
Session 2 — Secure Application Design

Least Privilege

Least privilege means a user, process, service or component receives only the permissions necessary to perform its legitimate function.

Examples: an application service account should not automatically have administrator/root privileges; a database account should receive only the tables/actions it requires.

Separation of Duties

Separation of duties divides sensitive responsibilities among different people, roles or components so that one actor cannot independently complete a high-risk operation.

Example: one role prepares a financial transaction while another role approves it.

Defense in Depth

Defense in depth uses multiple independent or complementary security controls. If one control fails, another can reduce the impact.

Example: secure coding + authentication + authorization + input validation + network segmentation + monitoring + backups.

Open Design

The open design principle says security should not depend on secrecy of the design or implementation. A design should remain secure even when an attacker knows how the system works, apart from secrets such as keys/passwords that are specifically intended to remain secret.

Minimizing Attack Surface Area

The attack surface is the collection of reachable interfaces, services, features, inputs and privileges that can potentially be abused. Reduce it by disabling unnecessary services, removing unused features, limiting exposed endpoints and minimizing privileges.

Remember the five design principles in this session: Least Privilege → Separation of Duties → Defense in Depth → Open Design → Minimize Attack Surface.

Session 3 — Input Validation

Input Validation Strategies

Input validation checks whether data conforms to the application's expected rules before processing it. Validation should be based on the application's actual business requirements.

Allowlist vs denylist

  • Allowlist: define what is permitted and reject everything outside the expected set. Generally preferred when feasible.
  • Denylist: define known-bad patterns. It can be useful as an additional control but is often incomplete by itself.

Validation dimensions

  • Type — integer, date, string, etc.
  • Length — minimum/maximum size.
  • Range — acceptable numeric/date boundaries.
  • Format — for example a constrained identifier format.
  • Business rules — whether the value makes sense in context.

Client-Side vs Server-Side Validation

Client-sideServer-side
Improves user experience and gives immediate feedback.Security boundary; must independently validate untrusted input.
Can be bypassed or modified by the client.Runs under application/server control.
Exam point: client-side validation is not a security boundary. Never rely on it alone.

Preventing XSS and Content Security Policy

Cross-Site Scripting (XSS) occurs when attacker-controlled data is interpreted as executable content in a victim's browser. Prevention includes context-appropriate output encoding, safe DOM APIs, careful handling of HTML and strong server-side input controls.

Content Security Policy (CSP) is a browser-enforced policy delivered through HTTP headers (or, in some cases, HTML metadata) that restricts permitted content sources and execution behavior. A strong CSP can reduce the impact of some XSS paths, but it should complement—not replace—safe output handling.

File Upload Validation

File uploads require validation because the application is accepting attacker-controlled content.

  • Allow only required file types.
  • Validate size limits.
  • Do not trust the client-provided filename or MIME type alone.
  • Generate safe server-side filenames.
  • Store uploads outside executable web roots where appropriate.
  • Apply authorization checks.
  • Scan/process files in an appropriately isolated environment when required.

Email Address Validation

Email validation should establish that the supplied value fits the application's expected format. Avoid trying to implement every possible detail of the full email standard with an overly restrictive regular expression. Also distinguish syntax validation from verification: a syntactically valid address does not prove that the mailbox exists or belongs to a particular user.

Use the OWASP cheat-sheet material supplied for the course as the lab reference. Practice mapping each validation problem to a concrete defense, then test the application with benign boundary cases and malformed input in the authorized lab.

Session 4 — Authentication and Authorization

Implement Proper Password Strength Controls

Password controls should encourage sufficiently strong passwords without relying on simplistic rules alone. Secure systems should store passwords using a dedicated password-hashing algorithm with a unique salt and appropriate work factor rather than reversible encryption or plaintext.

Consider length, breached-password defenses where available, rate limiting, secure password reset and multi-factor authentication for higher-risk accounts.

Authentication and Error Messages

Authentication answers “Who are you?” Error responses should not unnecessarily reveal whether a particular account exists. Consistent external messages can reduce account-enumeration opportunities while detailed diagnostic information remains available to authorized operators through secure logging.

Enforce Least Privileges

After authentication, the application should grant only the permissions required by the user's role and current task. Authentication alone does not grant authorization.

Authorization Checks on Static Resources

Static or directly addressable resources can also require authorization. Do not assume that hiding a link in the UI protects the underlying file/resource. The server or resource-serving layer must enforce access policy.

Authentication ≠ Authorization: authentication establishes identity; authorization determines what that identity is allowed to do.

Lab — OWASP Cheat Sheet Series

  1. Review authentication and authorization guidance.
  2. Identify login, logout, password reset and session boundaries.
  3. Test authorized lab accounts with different roles.
  4. Verify that every sensitive action performs an authorization decision.
  5. Check that error messages do not unnecessarily disclose account existence or internal details.
Session 5 — Session Management

Session ID Properties

A session ID links a series of requests to a server-side session. A secure session identifier should be unpredictable, sufficiently long, protected in transit and handled as a sensitive credential.

  • Use a cryptographically strong random source for session identifiers.
  • Regenerate the session ID after important privilege changes such as login to reduce session-fixation risk.
  • Expire sessions appropriately.
  • Invalidate sessions on logout where appropriate.
  • Protect session identifiers from unnecessary exposure.

Session Management Implementation

Session management covers creation, association, renewal, timeout and destruction of sessions. The server should treat session identifiers as authentication-related secrets.

Important controls include idle/absolute timeouts, secure logout, session rotation and protection against fixation and theft.

The Session Storage API

The browser sessionStorage API provides storage associated with a page/session context and is separate from HTTP cookies. Data in web storage is accessible to JavaScript running in the relevant origin, so sensitive authentication material should not automatically be placed there.

sessionStorage.setItem("theme", "dark");
const value = sessionStorage.getItem("theme");
sessionStorage.removeItem("theme");
Security point: if an XSS vulnerability exists, JavaScript-accessible storage can potentially be read. Storage choice must therefore be part of the threat model.

Lab — OWASP Cheat Sheet Series

Inspect session cookies in a controlled application. Verify their attributes, observe login/logout behavior, test session expiration, and document whether session identifiers change after authentication.

Session 6 — Error Handling

Information Exposure Through an Error Message

Error messages can accidentally disclose sensitive information such as filesystem paths, database details, stack traces, internal hostnames, software versions or query fragments. Production-facing responses should provide useful but appropriately limited information.

Detailed diagnostic information should be protected and available through controlled logging/monitoring rather than exposed directly to untrusted users.

Unchecked Error Condition

An unchecked error condition occurs when a program fails to handle an operation's failure state correctly. This can lead to crashes, inconsistent state, security bypasses or unsafe continuation.

try:
    result = perform_operation()
except ExpectedError:
    handle_failure()
else:
    use(result)

Do not silently ignore important failures. Decide which failures are expected, handle them deliberately and preserve useful diagnostic context without exposing secrets.

Lab — Error-prone tools

Use controlled, intentionally error-prone programs/tools. Trigger benign failure conditions such as invalid input, missing files and unavailable resources. Record the original failure, the user-visible response and the secure handling improvement.

Session 7 — Secure Deployment

VMs vs Containers vs Bare-Metal Isolation

TechnologyHigh-level isolation modelSecurity consideration
Virtual MachineGuest OS runs on virtualized hardware through a hypervisor.Strong isolation boundary in many deployments, but hypervisor/guest configuration still matters.
ContainerProcesses share the host kernel while being isolated using OS mechanisms.Lightweight, but the shared-kernel model means container isolation is different from a full VM.
Bare metalWorkload runs directly on physical hardware.No virtualization layer between workload and hardware, but OS/process isolation still matters.

Serverless

Serverless abstracts much of the underlying server management. Code is commonly executed in response to events or requests. Secure design still requires authentication, authorization, input validation, dependency management, logging, secrets management and least privilege.

Where and How to Keep Secrets

Secrets include API keys, passwords, tokens and private keys. Do not hard-code production secrets in source code or commit them to repositories.

  • Use a dedicated secrets-management mechanism where available.
  • Restrict access with least privilege.
  • Rotate secrets appropriately.
  • Keep secrets out of logs and error messages.
  • Use environment/configuration mechanisms carefully and protect the execution environment.

Automating the Deployment Process

Automated deployment reduces manual variation and can make security checks repeatable. Secure deployment pipelines should include source control, dependency checks, tests, secret scanning, infrastructure/configuration review and controlled promotion.

Core principle: deployment automation should make the secure path the repeatable path—not simply make deployment faster.

Lab — Secure Deployment Practice

  1. Deploy a harmless sample application to a disposable environment.
  2. Compare a VM-based and containerized deployment conceptually.
  3. Store a non-production test secret outside source code.
  4. Run automated tests before deployment.
  5. Verify logs do not contain the test secret.
  6. Document the security controls in the pipeline.
Session 8 — Attack Hardening, DoS/DDoS, Fail2ban, CAPTCHA & Secure Networks

Attack Hardening

Attack hardening reduces the likelihood and impact of attacks by removing unnecessary exposure, limiting resources, validating inputs, applying rate controls and designing resilient systems.

What is DoS/DDoS?

Denial of Service (DoS) aims to make a service unavailable or degraded. Distributed Denial of Service (DDoS) uses multiple sources, often a distributed set of compromised or otherwise participating systems, to generate the disruptive traffic.

Resource Exhaustion Fundamentals

Services have finite resources such as CPU, memory, connection slots, threads, file descriptors, bandwidth and application queues. An availability attack attempts to consume a resource faster than the service can recover it.

Defensive model: identify the scarce resource → limit consumption → reject or delay excess work → isolate components → monitor → scale or absorb traffic where appropriate.

SYN Flood

A SYN flood targets TCP connection establishment by causing the server to maintain state for many incomplete handshakes. Defenses can include operating-system/network protections, connection controls, filtering and upstream DDoS mitigation.

Full HTTP

The syllabus lists Full HTTP under DoS/DDoS. In this context, understand application-layer HTTP request flooding where complete HTTP requests consume server-side resources such as workers, application processing, database queries or bandwidth.

Slowloris

Slowloris is an application-layer availability technique that attempts to keep many HTTP connections open by sending requests slowly, tying up server connection resources.

ReDoS

Regular Expression Denial of Service (ReDoS) occurs when a vulnerable regular expression causes excessive backtracking/processing for crafted input. Secure defenses include avoiding pathological regex patterns, using safe regex designs, limiting input size and applying execution/resource limits where supported.

Fail2ban

Fail2ban is a defensive tool that can monitor logs for patterns associated with abusive behavior and temporarily block or restrict offending sources through configured actions.

It is a response mechanism, not a complete DDoS defense. It is most useful when the attack is visible in local logs and the host can safely enforce the response.

CAPTCHAs, reCAPTCHA, reCAPTCHA v3, XR privacy

A CAPTCHA is a challenge intended to distinguish automated activity from human interaction. Such controls can reduce some forms of automated abuse but should not be treated as a replacement for rate limiting, authorization or secure application design.

reCAPTCHA refers to Google's CAPTCHA-related service. reCAPTCHA v3 uses a risk/scoring approach rather than always presenting a visible challenge.

The PDF lists XR privacy but does not provide further explanation of that term in the supplied syllabus. Therefore, no additional interpretation is asserted here.

Introduction to Designing Secure Networks

Secure network design begins with understanding assets, trust boundaries and communication requirements.

  • Segment systems according to trust and function.
  • Expose only required services.
  • Use firewalls/security groups to restrict flows.
  • Protect management interfaces.
  • Encrypt sensitive traffic in transit.
  • Use monitoring and centralized logging.
  • Design for availability and recovery.
  • Apply least privilege to network access as well as user permissions.

Defensive DoS/DDoS lab

Use only a local/disposable lab and traffic-generation tools approved by your instructor. Do not run DoS/DDoS techniques against public or third-party systems. Instead, study server logs, connection limits, rate-limiting behavior and defensive configuration using controlled test traffic.
